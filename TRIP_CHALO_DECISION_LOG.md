## Product / Architecture (Phase 0)

**Decision:** Modular monolith on Next.js + Supabase + Cloudflare R2 +
Vercel, not microservices.
**Why:** Greenfield project, no current scale need; microservices would add
operational/deployment/monitoring complexity with no corresponding benefit
yet. Module folders (`auth`, `trips`, `memberships`, `invitations`, `media`,
`storage`, `chat`) preserve the option to extract later.
**Status:** CURRENT DECISION (foundational, restated consistently across
every subsequent phase, never revisited).

**Decision:** No public social features, no public trip discovery, in the
MVP.
**Why:** Core product is a *private* shared memory space; public discovery
would work against the stated purpose.
**Status:** CURRENT DECISION.

**Decision:** Prioritize near-zero infrastructure cost.
**Why:** Explicit user requirement at project kickoff ("keep near 0rs").
Vercel Hobby + Supabase free tier + R2 free tier (10GB, no egress fees) +
GitHub free was assessed as sufficient for MVP-stage usage.
**Status:** CURRENT DECISION — should be re-checked if usage grows past free
tiers.

## Database schema (Phase 2)

**Decision:** Six tables — `profiles`, `trips`, `trip_members`,
`invitations`, `media`, `messages`.
**Why:** Matches the product's core entities exactly; no table added
without a stated current purpose (explicit anti-overengineering rule from
Phase 0 applied here).
**Status:** VERIFIED — user confirmed migrations 0001–0008 applied and RLS
verified on all six tables at the start of the Phase 3 request.

**Decision:** `profiles.id` is both PK and FK to `auth.users.id`
(`ON DELETE CASCADE`), populated via a `SECURITY DEFINER` trigger
(`handle_new_user`) on `auth.users` insert.
**Why:** Standard Supabase pattern; keeps Auth as sole owner of credentials,
`profiles` as sole owner of application-level display data.
**Status:** VERIFIED (migration 0001, confirmed applied).

**Decision:** `trip_members` is the sole authorization gate for trip-scoped
data; **no direct client `INSERT` policy exists at all**. Rows are only
created by (a) the `add_trip_owner_as_member` trigger on trip creation, or
(b) the `accept_invitation()` function.
**Why:** This is what actually prevents a user from adding themselves to an
arbitrary trip — an absence of a matching RLS policy, not a check that
could be misconfigured.
**Status:** VERIFIED (migrations 0003 + 0007, confirmed applied).

**Decision:** Trip owner's `trip_members` row cannot currently be deleted —
neither by the owner leaving nor by anyone removing them.
**Why:** No ownership-transfer mechanism exists yet; allowing owner removal
without one would orphan the trip. Explicit interim limitation, corrected
into the RLS policy after the user caught the original (too-permissive)
version in review.
**Status:** VERIFIED (migration 0007, corrected version applied). Ownership
transfer itself is a **FUTURE PLAN**, not yet designed.

**Decision:** Invitations are email-targeted (`invitee_email`), not
user-ID-targeted; `invitee_id` resolves only at accept-time via a
`SECURITY DEFINER` function, matched against `(auth.jwt() ->> 'email')`.
**Why:** Invitee may not have an account yet at invite time. Using the JWT
claim instead of querying `auth.users` directly avoids an extra query
against a table the calling role may not be able to read, and reads a
value already cryptographically verified as part of the session.
**Status:** VERIFIED (migrations 0004 + 0007, confirmed applied, corrected
across two review passes).

**Decision:** Invitations have **no client-facing `UPDATE` policy or
grant** at all. All status transitions (`accept_invitation`,
`decline_invitation`, `revoke_invitation`) go through `SECURITY DEFINER`
functions that validate caller identity and current status before
transitioning.
**Why:** An earlier `UPDATE` policy attempt could have let a client alter
`trip_id`, `inviter_id`, `invitee_email`, or `invitee_id` directly.
Removing the client `UPDATE` path entirely (rather than trying to lock
individual columns with `WITH CHECK`) closes this off completely instead of
relying on getting every column-level check right.
**Status:** VERIFIED (migrations 0007 + 0008, confirmed applied).

**Decision:** `media` has **no client-facing `UPDATE` policy or grant**.
Rows are immutable via the Data API once inserted (`SELECT`, `INSERT`,
`DELETE` only).
**Why:** User-directed correction during Phase 2 review — no legitimate
client-side field update was identified once processing-status changes were
recognized as belonging to a future server-side process, not the browser.
**Status:** VERIFIED (migrations 0007 + 0008, confirmed applied).

**Decision:** `captured_at` and `uploaded_at` are stored as two separate
columns; `captured_at` is nullable and never overwritten by `uploaded_at`.
**Why:** Explicit product requirement — chronology must reflect when a
memory happened, not when it was uploaded, while still handling missing/
untrustworthy EXIF data via fallback (fallback logic itself is Phase 6
work).
**Status:** VERIFIED for the schema (migration 0005, applied). The
`COALESCE(captured_at, uploaded_at)` fallback query logic is a **FUTURE
PLAN** (Phase 6) — deliberately not implemented as a stored/generated
column or premature index.

**Decision:** All `SECURITY DEFINER` functions set `search_path = ''`,
fully qualify every table reference, and have `EXECUTE` explicitly
revoked from `PUBLIC` then granted only to `authenticated` (trigger-only
functions get no grant at all, since triggers don't need one).
**Why:** Prevents a caller from manipulating session `search_path` to
redirect an unqualified table reference inside a privileged function; makes
the "who can call this" surface explicit and auditable rather than relying
on default Postgres behavior (`EXECUTE` is granted to `PUBLIC` by default on
function creation).
**Status:** VERIFIED (migration 0007, confirmed applied).

**Decision:** `anon` role receives **no grants** on any of the six
application tables.
**Why:** No public/unauthenticated read path exists anywhere in the
product.
**Status:** VERIFIED (migration 0008, confirmed applied).

## Authentication (Phase 3)

**Decision:** `middleware.ts` renamed to `proxy.ts` (both the top-level file
and the `src/lib/supabase/` helper), exported function renamed
`middleware` → `proxy`.
**Why:** Confirmed via direct fetch of Next.js's own documentation during
review: as of Next.js 16.2+, `middleware.ts` is no longer discovered by the
framework at all (silent no-op, not a warning). The user's stack is 16.3.1.
This was a genuine correction of an earlier mistake in this project, not a
stylistic preference.
**Status:** VERIFIED — implemented, built successfully, manually tested,
and committed in e5b39a8 ("Complete Phase 3 authentication").

**Decision:** All server-side page/data protection uses
`supabase.auth.getClaims()`, never `getUser()` for this purpose and never
`getSession()` for authorization under any circumstance.
**Why:** Confirmed via direct fetch of Supabase's current SSR
documentation: `getClaims()` verifies the JWT signature against the
project's published keys on every call (locally, via cached JWKS, for
projects using asymmetric signing keys — the default for new projects), and
is Supabase's current recommended default for protecting pages/data.
`getUser()` remains correct when a fresh, server-confirmed user record is
specifically needed (not used for that purpose anywhere in this project
yet). `getSession()` only reads local cookie storage without revalidation
and must never be trusted for authorization.
**Status:** VERIFIED — implemented, built successfully, manually tested,
and committed in e5b39a8 ("Complete Phase 3 authentication"). Note: one official Supabase AI-prompt
guide file still showed `getUser()`-based proxy code during this same
research pass, indicating Supabase's own docs are mid-transition — worth
re-checking in future sessions rather than assuming this is permanently
settled.

**Decision:** Redirect targets from request input (`redirectTo` on login,
`next` on the auth callback) are validated with `isSafeRedirectPath` before
use — must be a same-origin path starting with `/`, not `//`, no `://`.
**Why:** Prevents open-redirect abuse (e.g. `/login?redirectTo=https://
evil.example.com`), caught during the Phase 3 review pass; the original
implementation passed these values straight into `redirect()` unvalidated.
**Status:** VERIFIED — implemented, built successfully, manually tested,
and committed in e5b39a8 ("Complete Phase 3 authentication").

**Decision:** `emailRedirectTo` for signup confirmation is built from
`NEXT_PUBLIC_SITE_URL` (authoritative) with `VERCEL_URL` as an automatic
fallback on Vercel deployments; the request's `Origin` header is
deliberately **not** used at all.
**Why:** Two-stage correction. First pass used `headers().get("origin")`
directly, which breaks when the header is absent (produces a broken
`null/auth/callback` link). Second pass kept `Origin` as first priority
with `NEXT_PUBLIC_SITE_URL` as fallback. Final correction (this decision)
removed `Origin` entirely, since it's client-suppliable and this value
becomes part of a link emailed to the user — it should come only from
server-controlled configuration.
Status: VERIFIED — implemented, built successfully, manually tested, and committed in e5b39a8 ("Complete Phase 3 authentication").

**Decision:** Password reset flow is out of scope for Phase 3.
**Why:** Not part of the originally stated Phase 3 goal list (signup/
login/logout/session/protected-routes/profile-integration). Flagged
explicitly as a known gap rather than silently added or silently omitted.
**Status:** FUTURE PLAN — no phase currently assigned.
